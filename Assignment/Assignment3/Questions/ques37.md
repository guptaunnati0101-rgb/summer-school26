IoT devices are frequent targets because they are often deployed with weak default credentials and rarely receive security patches. The most common Wi-Fi attack vectors include exploitation of WPA2 vulnerabilities such as KRACK (Key Reinstallation Attack), which forces reuse of encryption nonces during the 4-way handshake, allowing an attacker to decrypt traffic. Another major vector is the evil twin attack, where an attacker sets up a rogue access point broadcasting the same SSID as a trusted network; unsuspecting ESP32 devices configured to auto-connect by SSID name can associate with the attacker's AP instead, exposing credentials and data to interception.
To secure ESP32 Wi-Fi connections, best practice starts with migrating to WPA3, which uses Simultaneous Authentication of Equals (SAE) to resist offline dictionary attacks and provides forward secrecy, so a compromised password doesn't expose past traffic. For device-to-server communication, certificate pinning ensures the ESP32 only trusts a specific server certificate (or its public key), preventing man-in-the-middle attacks even if a malicious CA certificate is installed on the network. Devices should also disable auto-connect to open or unknown networks and validate the AP's BSSID, not just the SSID.
Hardcoding Wi-Fi passwords and API keys directly in source code is dangerous because that code is frequently pushed to public GitHub repositories, embedded in shared .ino files, or extractable from flash memory via UART/JTAG debugging. Anyone with the binary or repository access gains instant network credentials. Storing secrets in a separate, git-ignored config.h file, or better, in encrypted NVS (Non-Volatile Storage) partitions, keeps secrets out of version control and harder to extract.

References: (1) Vanhoef, M. & Piessens, F., "Key Reinstallation Attacks: Forcing Nonce Reuse in WPA2," ACM CCS 2017. (2) Wi-Fi Alliance, "WPA3 Specification," wi-fi.org.
